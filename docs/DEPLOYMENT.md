# Deployment

Target platform: **Render** (`render.yaml` at the repository root is a Blueprint).
Nothing here is Render-specific in the application itself — it is a standard
Python service, a static site and a worker, so any comparable platform works.

> **No secret is committed.** Every value in `render.yaml` is either generated by
> Render or marked `sync: false`, meaning you set it in the dashboard.

## Before you deploy

### 1. Object storage — required

Create a **private** bucket with any S3-compatible provider (AWS S3, Cloudflare
R2, Backblaze B2, MinIO). Note the bucket name, region, endpoint and an access
key pair scoped to that bucket only.

The service **refuses to start in production with filesystem storage**. This is
deliberate: a container disk is ephemeral, so every deploy would silently delete
patient retinal images.

### 2. Decide the model provider

Leave `RS_MODEL_PROVIDER=development` for the first deploy. The placeholder is
clearly labelled in every UI surface. Switch to a real model afterwards by
registering it — see [TRAINING_A_REAL_MODEL.md](TRAINING_A_REAL_MODEL.md).

### 3. Choose a bootstrap administrator

`RS_SEED_ADMIN_EMAIL` must be a **routable-looking address**. Reserved TLDs
(`.local`, `.test`, `.example`, `.invalid`) fail email validation and produce an
administrator account that can never sign in. `init_db` refuses to create a
production admin with the default password.

## Deploy

1. **Render Dashboard → New → Blueprint**, point it at this repository.
   It reads `render.yaml` and proposes the database, API, dashboard and worker.

2. **Set the `sync: false` variables** on `retinasight-api`:

   | Variable | Value |
   |---|---|
   | `RS_S3_BUCKET` · `RS_S3_REGION` · `RS_S3_ENDPOINT_URL` | your bucket |
   | `RS_S3_ACCESS_KEY_ID` · `RS_S3_SECRET_ACCESS_KEY` | scoped key pair |
   | `RS_PUBLIC_BASE_URL` | `https://retinasight-api.onrender.com` (no trailing slash) |
   | `RS_CORS_ORIGINS` | the dashboard origin, comma-separated |
   | `RS_SEED_ADMIN_EMAIL` · `RS_SEED_ADMIN_PASSWORD` | your admin |

   The three signing secrets are generated by Render — do not set them by hand.

3. **Set `VITE_API_BASE_URL`** on `retinasight-dashboard` to
   `https://retinasight-api.onrender.com/api/v1`.
   This is a **build-time** variable: changing it requires a rebuild, not a restart.

4. **Deploy the API first.** Its start command runs `alembic upgrade head`, so
   the schema exists before anything else connects.

5. **Seed the RBAC policy and administrator** — once, from the API service shell:

   ```bash
   python -m scripts.init_db
   ```

   Idempotent; safe to re-run.

6. **Deploy the dashboard and worker.**

## Verify

```bash
curl https://retinasight-api.onrender.com/health/ready
```

Expect `{"status":"ready","database":"connected"}`. This probe performs a real
database round-trip, so it fails loudly if the database is unreachable.

Then sign in as the administrator and check **Admin → System health**:

| Check | Expected |
|---|---|
| Database | connected · postgresql |
| Object storage | available · s3 |
| Model | loaded |
| Development model badge | present until a real model is registered |
| Validation | **not clinically validated** ← correct |

`/docs` returns 404 in production. That is intentional.

## Worker

The worker is optional. In `sync` mode the API runs inference inline, which is
fine at low volume.

Switch to asynchronous processing by setting `RS_INFERENCE_MODE=worker` on the
API service. The worker then claims sessions in `ready_for_inference`, runs
inference, Grad-CAM and the risk engine, and writes results back.

It is safe to run more than one: claims are made in a committed transaction
using `SELECT … FOR UPDATE SKIP LOCKED`, and a session abandoned by a crashed
worker returns to the queue after 15 minutes.

---

## Operational notes

**Migrations** run automatically on API start. For a large migration, deploy with
the worker scaled to zero first so it cannot write against a half-migrated schema.

**Free-tier instances sleep.** A cold start takes 30–60s, which a health worker
on a poor connection will experience as a timeout. The offline queue absorbs
this — work is never lost — but use a paid instance for anything real.

**Rate limiting is per-process.** With several replicas the effective login
limit multiplies by replica count. Put a shared limiter at the edge if you need
a hard guarantee.

**Backups.** Enable point-in-time recovery on the database. Retinal images live
in object storage, so back that up too — the database alone is not a complete
backup of patient data.

---

## Rolling back

Render keeps previous deploys; roll back from the dashboard. **Check first
whether the deploy included a migration** — application rollback does not undo a
schema change. Reverse it explicitly:

```bash
python -m alembic downgrade -1
```

## Not covered here

This is deployment, not clinical readiness. Before real patients:

- a clinician must review the risk thresholds and referral timeframes in
  **Admin → Configuration** — they are engineering defaults
- the model must carry real validation evidence
- data-protection obligations in your jurisdiction must be met
- a penetration test is advisable; none has been performed
